# 四路MPY控制：能跑，不等于已经适合丝滑的小车

这次把整周期补测了一遍。结论：静态跟随可用，但启动响应偏慢，20ms实时预算还比较紧；不能仅凭四路能转和末段转速准，就说遥控车一定跑得顺。也没有证据证明必须放弃MPY。

## 好的和还不好的地方

- 好：此前五组正反转/低速的20个组合，后5秒平均误差与波动都满足基础标准；最大平均误差约0.86RPM。
- 还不好：有一次38.57%观测启动超调；首次达到目标90%用时约1.6～3.5秒（10Hz遥测估计），手控跟手性偏慢。160/200ms滚动测速窗口还有约70/90ms的等间隔线性平均群延迟，20ms输出节拍不等于20ms反馈响应。

## 新补测什么

微秒装饰器沿用ticks_us/ticks_diff，完整审计统计每个周期的核心更新、I2C、PID、实际ADC采样、周期工作、实际周期、调度迟到、四路输出函数完成时差及显式GC。随后做轻量统计对照，再清理旧REPL模块引用后重复轻量试验。两段分别四路正向组合、反向组合，第二段每2秒显式GC一次；都是台架加真实USB遥测，没有Wi-Fi/遥控/路面负载。

工作时间从控制tick开始，到这次ADC、检查、遥测等完成为止，不含主动等待下一周期。I2C/PID是核心更新的子集，不与整周期重复相加。所有时间均为包含中断、GC和测量开销的墙钟时间，不是纯CPU占用率。分位数来自100us桶的保守上界，溢出桶用观测最大值作上界；调度周期/迟到由毫秒时钟记录。超过20ms统计的是单次工作超预算，不等同于精确的端到端命令deadline miss。零跳过完整周期也不代表没有超时。

## 能怎么判断

清理残留后的轻量测量仍出现P99超过20ms，最大约24.7ms。这只能证明当前测试环境下余量偏紧，不是生产固件最坏时间上界。完整审计平均四路输出函数完成时差约8.4～8.6ms、最坏约16.1ms；这是第一/第四个set_speed返回的时差，不是仪器测出的PWM边沿。清理残留后显式GC约3.8ms，清理前约6.4～7.1ms，说明内存状态会影响测试结果。多轮复测期间电源/电机温度等也未严格控制，因此对照不当作单因素因果证明。

## 下一步优化优先级

1. 先处理起步与目标变化：标定每路正反向死区/静态前馈，配合有界的加减速斜坡；急停走独立快速停机。不能指望微秒级加速解决秒级起步。
2. 把测速窗口改为预分配环形缓冲、维护累计计数/时间；避免每周期建立元组、生成器和重复sum。遥测用固定缓冲，减少热路径分配。
3. 控制tick优先，ADC、日志和通信按剩余预算执行。GC放到有余量的时段，并继续测分布；不长期关闭GC。
4. 评估PCA连续通道批量写与减少重复写，但要保留换向关断顺序、模式隔离和异常停机语义；必须再次上板验证。
5. 这些都做完仍不足，再考虑将已定位的热点转native/viper/C；目前PID调用均值约1.3～1.5ms，不是唯一耗时。

## 真车还缺的证据

需要在真实遥控链路、转向/舵机和地面带载都运行时，测命令到首路/末路输出延迟、周期迟到、速度响应、启停/换向和至少数分钟的长尾。建议本项目下一轮把20ms下P99工作量压至约14ms以内、长时最大工作量小于20ms，作为预留业务余量的工程目标；这是建议值，不是玩具行业标准。

所以目前评价是：台架匀速基础合格，动态响应与实时余量仍需优化；整车丝滑尚未验证。
